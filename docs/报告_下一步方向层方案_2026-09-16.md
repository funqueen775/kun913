## 3. 核心主张：把"建议"改成"机会预告"

### 为什么不能用常规写法

一个测评产品最容易滑向这句："你在沟通协作上偏弱，建议多主动表达。"
这句话同时踩了三条线：① 是人格断言；② "偏弱"隐含阈值；③ "建议你"是命令句。

### 改成什么

**同一个事实，换一个说法**：

> 原：你沟通协作偏弱，建议多主动。
> 改：六项能力里，「沟通协作」和「主动担当」这两处，你累积的正向选择最少。
> 　　这类场合后面还会遇到。

差别在哪：
- **点名不给数**（"最少"是相对事实，不暴露门槛，也不暴露满分口径 —— 见 §6）
- **不解释成"你是什么人"**，只说"累积的正向选择少"
- **"后面还会遇到"是机会预告，不是命令** —— 玩家自己会决定怎么做

这条原则贯穿全部 5 类方向。

## 5. 五类方向的判定表

统一输出形状（每条）：

```jsonc
{ "kind": "keep" | "watch",     // 保持 / 留意
  "title": "…",                  // 短标题（≤8 字）
  "line": "…",                   // 一句话（行为语言，无阈值）
  "evidence": [ EvidenceRef ] }  // 复用既有 EvidenceRef，不新造
```

`kind` 只有两值，是为了让"强项"也有位置 —— 否则"没有问题"的项无处安放（见 §8 反面清单）。

### 方向 A · 守住的场合
- **触发**：机会数 **≥ 3**（沿用 `topics.py` 的"≥3 条证据才说"既有口径，不新造门槛）
- **原料**：`frames` 两组计数
- **输出**：`"9 次可以甩锅的场合，你守住了 3 次。"`
- **kind**：守住数 == 机会数 → `keep`；否则 → `watch`
- **要带的证据**：该类场合对应的决策 `EvidenceRef`
- **反面**：机会数 < 3 → **整条不出现**（小样本不下结论）

### 方向 B · 六柱相对最薄 ⭐ 现在唯一能出的
- **触发**：`radar` 里有效柱 **≥ 2**（少于 2 根无法比较）
- **筛候选**：只取 `evidence_count ≥ 3` 的柱
- **排序**：按 `score` **升序**（最低 = 累积正向选择最少）
- **取几条**：最少的那根 + 与其并列的（**最多 3 条**）
- **并列规则**（实跑第一局就会撞上：沟通协作 3 与主动担当 3 并列）：
  → **并列全取**，不人为挑一个。理由：任选一都会引入未声明的偏好。
- **输出**：`"六项能力里，「沟通协作」和「主动担当」这两处，你累积的正向选择最少。"`
- **kind**：恒为 `watch`
- **反面**：
  - **不给百分数、不给档位、不给满分** —— 只说"最少"
  - **不解释成"你不擅长 X"** —— 只说"累积的正向选择最少"
  - 若所有柱 `score` 相等 → **整条不出现**（没有相对差异就没有方向）

### 方向 C · 精力代价
- **触发**：`dangerZoneCount ≥ 1`
- **原料**：`dangerZoneCount / pushedThroughCount / recoveryWays`
- **输出**：`"你有 3 次把自己用到危险区，其中 2 次选了硬扛。恢复里 1 次是你主动选的，2 次是被迫停下。"`
- **kind**：`pushedThroughCount > 0` → `watch`；否则 `keep`
- **反面**：**不给 H 数值、不给危险线阈值**（沿用 `_energy_ledger` 既有口径）
- **现在恒不出现**（全 0）

### 方向 D · 考核窗序列
- **触发**：`windows ≥ 1`
- **输出**：`"7 个考核窗，你过了 4 个。"`；若有未过 → 复用既有 `label`（"中途卡过"等），不新造词
- **kind**：有未过 → `watch`；全过 → `keep`
- **反面**：**不给阈值**（`promotion.py` 红线：阈值数字永不出现）；`PLACEHOLDER_CUMULATIVE_MIN` 等占位值**不得出现在任何文案里**
- **现在恒不出现**（`windows: []`）

### 方向 E · 情境不一致
- **触发**：`bigfive` 里存在 `consistency == "situational"` 的项
- **输出**：直接用既有常量 `CONSISTENCY_NOTE`（`report/__init__.py:26`），**不另写文案**
- **kind**：`watch`
- **反面**：**不给大五点值**（`behavior` 是推断值）；只报"有条件"这一档
- **现在恒不出现**（自评埋点未采集）

## 6. 排序与取舍：怎么不暴露阈值和权重

这是本方案最容易做错的地方，单列一节。

**规则 1 · 排序依据是"证据条数"，不是"严重程度"。**
按严重程度排需要给每类方向定权重 → 权重会暴露标定 → 违反"阈值永不出现"。
按证据条数排是纯可观测的，且天然把"料最足的方向"排前面。

**规则 2 · 用"相对比较"替代"绝对门槛"。**
"六柱里最少的那两根"是相对事实，不需要任何门槛数字。
若改用"低于 X 分的柱"，就必须公开 X —— 所以**不用**。

**规则 3 · 三类降级不出现，而不是降级显示。**
沿用 `topics.py` 的 `displayable` 机制（`n < threshold` → 报告层整体不渲染）：
- 机会数不足 → 不出现
- 无相对差异 → 不出现
- 依赖的原料为空 → 不出现
**不用"暂无数据"占位**（铁律：证据不足的模块整体不出现）。

**规则 4 · 整层空则整层不出现。**
5 类全不出内容 → `directions` 返回空数组，客户端不渲染这一层。
（按 §2，**现在第一局就是这个状态**，只有方向 B 一条。）

## 7. 措辞红线（词表）

生成文案前**必须过这张表**，建议直接做成单测断言（见 §10）。

### 禁用词（出现即视为 bug）

| 类别 | 禁用 |
|---|---|
| 人格断言 | 你适合 / 你不适合 / 你天生 / 你的问题是 / 你就是 |
| 命令句 | 建议你 / 你应该 / 必须 / 一定要 / 要多 / 少去 |
| 阈值泄露 | 低于 / 高于 / 达标 / 及格线 / 超过 N 分 / 满分 |
| 岗位结论 | 适合做 / 推荐做 X 岗位 / 匹配度 |
| 否定词 | 不行 / 差 / 弱 / 失败者（对人不合格） |

### 允许句式（只有这三种）

1. **计数并置**：`N 次…里，M 次…` —— 两个可观测死数字
2. **相对比较**：`六项里，（点名）最少 / 最好` —— 不给数值
3. **机会预告**：`这类场合后面还会遇到` —— 陈述事实，不命令

### 一个刻意的取舍
**不给"守住率"这个百分数**。虽然"3/9"两个数字摆一起玩家自己能算，但我们不替他算 ——
因为比率是**推断值**，按铁律只能给档位；而给档位就要定义档位门槛。**两个死数字并置**既绕开了门槛，
又比档位更准确。

## 8. 反面清单：什么时候**不**用这套

| 不要做 | 原因 |
|---|---|
| 不要用它替代岗位推荐 | `market` 层是另一件事（要 JD 语料），别混进 `directions` |
| 不要在 `directions` 里放人格结论 | 人格归 `persona.layers`，混进来就变成"第二份画像" |
| 不要为了凑条数放低门槛 | 门槛一松就回到"小样本下结论"，这是原设计最防的事 |
| 不要给"改进后的预期收益" | 无法验证，属于承诺，产品不背这个 |
| 不要做"评分/打分" | `directions` 是**方向**，不是分数；一旦有分就能被优化/刷分 |
| 不要用"暂无数据"占位 | 与"证据不足整体不出现"矛盾 |
| 不要默认排序按游戏内月份 | 月份是玩家自己的时间线，跨玩家不可比；排序只用证据条数 |
| 不要在文案里出现 `cap` / `score` / `threshold` 字段名 | 内测口径不外泄 |

## 9. 契约与代码落点

### 契约（`contracts/openapi.yaml`）
**新增顶层字段**（不改既有结构）：
```yaml
    Report:
      properties:
        …
        directions:                  # 新增，可选
          type: array
          description: >
            下一步方向（前瞻层）。与前三层不同类：前三层是"当下画像"，
            本层是"同类场合下次还会来，上一局命中率如何"。按证据条数降序，
            无内容时为 []，客户端不渲染。
          items: { $ref: '#/components/schemas/GrowthDirection' }
    GrowthDirection:                 # 新增 schema
      type: object
      required: [kind, title, line]
      properties:
        kind: { type: string, enum: [keep, watch] }
        title: { type: string, maxLength: 16 }
        line: { type: string }
        evidence:
          type: array
          items: { $ref: '#/components/schemas/EvidenceRef' }
```
**安全性已核实**：`Report` 是 `type: object` + `properties`，**没有** `additionalProperties: false`
→ 加可选字段**不破坏**既有校验，老客户端忽略未知字段。

**为什么放顶层、不放 persona 层**：① `persona` 是"11 模块"既有口径，塞第 12 个会打乱；
② 语义上它是**前瞻**，与"画像"不同类；③ 加顶层可选字段比改既有对象结构更安全。

### 代码
| 文件 | 动作 |
|---|---|
| `app/report/directions.py` | **新建**。5 个 `_dir_*` 函数 + `build_directions(state, reg, persona)`。纯函数、不读外部文件 |
| `app/report/__init__.py` | `build()` 里加一行 `"directions": directions.build_directions(...)`；`directions` 只读 `state` 与**已算好的** `persona` 子对象，**不重复计算** |

**关键约束**：`directions.py` 只消费 `build()` 已经算出来的结果，**不重新调 `bayes` / `radar` /
`topics`** —— 否则同一份数据被算两次，一旦两处口径漂移就会自相矛盾。

### 明确不动的
- 引擎（`app/engine/`）：**零改动**。本层是纯读取，不新增任何 state 字段
- 打分卡 / 剧情数据：**零改动**
- 现有 11 模块：**零改动**
- 前端：**零改动**（前端还没做，见 §11）

| 实算(仅已玩) | **2 根并列**：沟通协作、主动担当(25) | 沟通(25) = 担当(25) < 技术(30) < 执行(33) < 原则(44) < **抗压(50)** |

**三个必须注意的结论**：
1. **表值会把抗压韧性从"最强"误判成"第三薄"** —— 表值 cap=14 是实算 cap=4 的 **3.5 倍**，
   该柱在两种口径下排名**首尾颠倒**。这是最危险的一处。
2. **表值系统性压低所有人**：分数全落在 3–15%，看起来"全面溃败"；实算(全) 是 6–25%；
   实算(仅已玩) 是 25–50%，分布最健康。
3. **表值 cap 是实算 cap 的 1.1–3.5 倍**，六柱倍率还不一样 → 不是简单的整体缩放，
   **会改变柱与柱的相对关系**，因此不能靠"乘个系数"修补。

→ **这不是精度问题，是会给玩家看反的结论。口径必须在方向层开工前定死。**

（另注：`radar.py:12` 已注明抗压韧性"样本最薄，须由 H 行为记录补强"，
与上表该柱 cap 仅 4 分吻合 —— 这根柱本身就该谨慎下结论。）

**要你拍板的**：
1. 雷达满分口径选**哪一种**？（风险 1、2 的根）—— **我的推荐见下**
2. `directions` 放**顶层**（本方案）还是塞进 `persona` 当第 12 模块？（我按 §9 定为顶层，
   纯技术结构，不必占用决策）
3. 本层**现在就做**，还是**等剧情补厚再做**？（我按 §2 建议后者）

### ✅ 对口径问题的推荐：**实算，且按"玩家实际走过的事件"算 cap**

**推荐 C：`compute_caps` 的输入从 `reg.decision_events()`（全量卡）换成玩家 `events_done`。**
三种口径的取舍：

| 口径 | 优点 | 致命问题 |
|---|---|---|
| A 表值 | 静态、可预期 | **已严重失真**（是实算的 1.1–3.5 倍，抗压韧性 3.5 倍）；卡一改就永远错；会把抗压韧性**判反** |
| B 实算(全量卡) | 自动跟随真实卡；跨玩家可比 | 玩家只走 9 件、cap 按 23 件算 → **人人虚低**（6–25%），剧情补齐期间全是无意义的低分 |
| **C 实算(仅已玩)** ⭐ | 自动跟随；语义最准（"你走过的路上拿满了多少"）；分布健康（25–50%）；六柱 cap 基于同一批事件 → **柱间比较最公平** | **跨玩家不可比** |

**为什么 C 的缺点可以接受**：方向 B 只比较**同一个玩家自己六柱之间的相对高低**，
本来就不跨玩家 —— 而 C 恰恰让这个比较最公平（六柱 cap 同源于同一批事件）。

**什么时候必须回退到 B**：将来要做跨玩家对标（分位、排行榜）时。
→ 建议：**方向层用 C；等剧情补完、所有玩家都走完整条线，再切回 B 做对标。**

**顺带建议**：删掉 `constants.RADAR_CAP_IN_DOC`（表值）与 `radar.py` 注释里 `40/37/35/34/30/8`
这套过期数字。两套并存是长期隐患 —— 任何人随手换一下就会得出相反的结论。
