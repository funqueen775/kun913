# 职场小镇 前后端协作架构与开发规范

## 1. 用途和当前目标

本文件与 `职场小镇开发文档V1.docx` 是后续开发的共同依据。开发文档定义剧情、场景与活动；本文定义前后端边界、数据流、接口与 Git 协作规则。接口字段以 `contracts/openapi.yaml` 为唯一准则。

第一阶段目标是完成可测的第一幕闭环：玩家进入区域，触发主线事件，完成选择，事件上传，后端返回新状态，最后可生成报告。当前 Godot 只验证玩法和交互，职业结论不由客户端决定。

## 2. 总体架构

```text
Godot 游戏前端 / 后续鸿蒙客户端
  地图、移动、NPC、剧情演出、选择界面
                 |
                 | HTTPS JSON
                 v
后端 API
  会话、存档、剧情进度、事件校验、规则评分、报告生成
                 |
                 v
数据库
  用户会话、事件流水、状态快照、报告
```

Godot 是当前原型的显示和交互层。`entry/` 内 ArkTS 工程只是鸿蒙 Web 容器，加载 Godot 导出文件，不承担评分和剧情状态。未来若改为原生 ArkTS，仍复用 API、剧情配置、美术与碰撞数据。

## 3. 职责边界

| 范围 | 前端负责 | 后端负责 |
| --- | --- | --- |
| 地图与角色 | 地图、碰撞、移动、镜头、触控、NPC 演出 | 不负责 |
| 剧情呈现 | 展示事件、选项、反馈、下一步提示 | 返回可展示的事件和状态 |
| 选择提交 | 生成稳定 `eventId`，提交选择和耗时，断网时重试 | 幂等接收、校验、保存事件 |
| 游戏状态 | 缓存并展示服务端状态 | 会话、章节、解锁、好感、精力、flag 的唯一权威 |
| 职业测评 | 展示维度变化和报告 | 用确定性规则计算分数和报告数据 |
| AI 文本 | 可展示后端返回文本 | 可用于对话润色或报告表达，不能决定分数和结局 |

主线选择进入职业测评分。自由活动主要影响好感、精力、开放性、特殊 flag 与后续文案。客户端本地分数只用于预览，最终结果以服务端为准。

## 4. 目录和内容 ID

```text
data/town/                       地图区域、碰撞与导航，前端维护
data/story/                      后续新增：剧情内容与活动配置，产品/前端维护
scripts/                         Godot 交互实现，前端维护
contracts/openapi.yaml           接口契约，前后端共同评审
contracts/fixtures/              Mock 请求/响应，前端可离线开发
backend/                         后端源代码、迁移和部署说明，后端维护
docs/                            项目文档，双方共同维护
```

剧情内容必须有稳定 ID，例如 `M1-E01`（第一幕第一个主线事件）、`S1`（单人自由活动）、`D1`（双人活动）。区域统一用 `A` 到 `H`，不得只靠中文名称做程序判断。

## 5. 接口约定

基础路径为 `/api/v1`。开发期地址由前端配置，不写死在 Godot 场景中。

| 接口 | 用途 | 调用时机 |
| --- | --- | --- |
| `POST /sessions` | 创建或恢复一次测评会话 | 进入游戏 |
| `GET /sessions/{sessionId}` | 获取完整状态 | 启动和断线恢复 |
| `GET /sessions/{sessionId}/next` | 获取当前主线或自由活动 | 进入新节点 |
| `POST /sessions/{sessionId}/events` | 记录选择、活动、入区等事件 | 操作完成后 |
| `POST /sessions/{sessionId}/report` | 请求最终报告生成 | 全部主线完成后 |
| `GET /sessions/{sessionId}/report` | 读取已生成报告 | 报告页 |

完整 JSON 字段、枚举和返回码见 `contracts/openapi.yaml`。新增或修改字段必须先更新契约和 fixture，双方确认后才修改各自代码。

### 事件提交规范

每一次可能影响状态的行为均发送一条事件，至少包含以下数据：

```json
{
  "eventId": "uuid，由前端生成且永不复用",
  "eventType": "main_choice",
  "contentVersion": "v1",
  "clientTime": "2026-09-13T10:00:00+08:00",
  "durationSeconds": 42,
  "payload": {
    "storyId": "M1-E01",
    "choiceId": "M1-E01-C02",
    "regionId": "A"
  }
}
```

后端按 `sessionId + eventId` 幂等处理。同一个 `eventId` 重传时必须返回第一次结果，不重复加分或推进剧情。客户端网络失败时保存事件并重试，不要生成新的 `eventId`。

## 6. 状态和评分规则

服务端状态至少包含：`chapterId`、`currentNodeId`、`completedStoryIds`、`completedActivityIds`、`unlockedRegionIds`、`energy`、`npcAffinity`、`flags`、`scoreSummary`。

评分规则必须满足：

1. 同一组事件得到同一分数和报告结论。
2. 每个维度能追溯到具体主线事件和选项。
3. 分数规则版本化，例如 `scoringVersion: v1`。
4. LLM 只能把已有结构化分数写成自然语言，不得自行加减分。
5. 后端保存原始事件流水，报告可以重新计算。

第一版建议只保留 4 到 6 个可解释维度：协作、沟通、问题解决、执行推进、学习适应、压力应对。每个选项预先配置固定权重。

## 7. 两边各自的开发顺序

前端：先完成地图移动、区域识别、NPC 交互和触控；用 `contracts/fixtures/` 完成主线事件与自由活动弹窗；再接 `/next` 和 `/events`，最后加入本地待重传事件队列、加载和失败状态。

后端：先实现 `/sessions`、`/next`、`/events`；设计事件表、会话快照表、规则配置表和报告表；实现事件幂等、状态推进和固定评分；最后才接入 LLM 文案润色，并保留不使用 LLM 的降级报告。

## 8. Git 和联调规则

- 一个 GitHub 私有仓库，前端和后端都在此目录协作。
- `main` 只放可运行版本；从 `feature/功能名` 分支开发，经 PR 合并。
- 不提交 `.godot/`、`oh_modules/`、`build/`、`output/`、`.env`、`.hap` 等生成物和密钥。
- 提交信息使用 `feat:`、`fix:`、`docs:`、`chore:`，例如 `feat: submit main choice event`。
- 一次提交只解决一个目的。改接口必须同时改 `contracts/openapi.yaml` 和 fixture。
- 合并前至少验证 Godot 能启动；接口变更额外验证 fixture 与后端测试通过。
- API Key、数据库密码和正式服务地址只放本机 `.env`，绝不提交 GitHub。

## 9. 第一轮联调验收

完成以下 6 条即说明基础打通：

1. 前端创建 `sessionId` 并显示当前节点。
2. 玩家走入 A 区，打开 `M1-E01`。
3. 用户选择 `M1-E01-C02` 并上报事件。
4. 重复点击或网络重试不重复计分。
5. 前端根据服务端返回状态显示下一节点或自由活动。
6. 刷新或重启后可用 `sessionId` 恢复进度。

## 10. 鸿蒙交付原则

当前鸿蒙验证继续使用 `entry/` 的 ArkTS 壳加载 Godot Web 导出包。每完成一个可玩章节，就在鸿蒙模拟器或真机走一遍“进入地图 -> 选剧情 -> 上报接口 -> 恢复状态”的竖切验证。后端接口和剧情配置不得依赖 Godot，确保未来改为原生 ArkTS 时无需重做服务端。
