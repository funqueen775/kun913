# 熊心壮职 · 记忆系统设计说明 V1

> 后端实现依据。对应《0909 游戏机制与情绪价值设计说明 V1》§5.2 / §5.3 / §9 / §10、
> 《前后端协作架构与开发规范》§5 接口约定、`contracts/openapi.yaml` 的 memory / chat / messages 三组接口、
> `backend/engine_core`（M0+M1）既有的事件流水与 `memory_tags`。
> 接口字段以 `contracts/openapi.yaml` 为准；本文只规定后端内部设计与口径。

## 1. 目标与边界

记忆系统要交付三件事（对应机制文档 §9 的情绪闭环"被记住"）：

1. **NPC 记得**：四层记忆（事实 / 关系 / 状态 / 社交）可被对话引用，且每条记忆能回放到具体事件；
2. **NPC 主动**：状态 / 关系 / 剧情 / 记忆四类触发器在正确的时机生成主动消息，带冷却与优先级，不轰炸玩家；
3. **报告可复算**：测评证据与游戏记忆物理隔离，同一条事件流水能同时导出两者且结果确定。

明确不做（对应机制文档 §12.2）：不做跨玩家的"社会记忆"；不做向量 / 图谱检索（见 §2 原则 4）；
聊天记录永不进测评证据；记忆不影响评分。

## 2. 设计原则（四条，改设计前先读）

1. **记忆是事件流水的只读投影，不是可变状态。**
   服务端不为"NPC 记住了什么"建可变表。写入侧只有事件（`eventId` 幂等追加）；
   读取侧按 NPC 现算。收益：报告可复算、存档恢复必然正确、记忆与事实永不脱节。
2. **确定性优先。** 同一组事件必须得到同一份记忆和同一份报告。凡需要 LLM 的环节
   （措辞润色）只允许改写表达，不允许产生或删改事实；且必须有无 LLM 的模板降级。
3. **游戏记忆与测评证据物理隔离。** `memory_game`（NPC 对话 / 记忆墙用）与
   `evidence_assessment`（报告证据链用）分开存储，宁可字段重复也不共用，防止把聊天
   内容喂进测评（机制文档 §10 防污染规则的落地形式）。
4. **检索按结构化键，不按语义。** 四层记忆各自有明确的结构化查询键
   （NPC + tag + 时间窗），数据规模上限 = 107 个决策点 × 48 个月，全量现算毫秒级，
   不需要向量库、缓存或外部记忆框架。

## 3. 总体结构

```text
事件流水 events（只追加，eventId 幂等）      公开账本 / 关系阶段（当前状态）
        │                                        │
        ▼                                        ▼
┌──────────────────────────────────────────────────────────┐
│  app/engine/memory.py   四个只读投影（纯函数）             │
│   fact_memories / relation_memory /                       │
│   state_memory  / social_stances                          │
└──────────────────────┬───────────────────────────────────┘
                       ▼
            MemoryReadPort（读接口）
             │                      │
             ▼                      ▼
   ① NPC 对话组装（M4）    ② 主动消息触发器调度器（M3）
             │                      │
             ▼                      ▼
      LLM 润色 + 模板降级      trigger_log（冷却可复算）
```

排序口径沿用规范：**跨玩家对齐、回放用 `seq`；给玩家看的叙事时间用 `month`。**

## 4. 统一记忆条目

所有层共用一个结构，`fact` 字段是模板生成的确定文案（不是 LLM 输出）：

```python
@dataclass(frozen=True)
class MemoryItem:
    seq: int          # 事件流水序号，回放与排序的唯一依据
    month: int        # 游戏内月份 1..48，给玩家看的叙事时间
    npc_id: str       # 记忆归属（wang_ge / xiao_lin / lao_zhou / xiao_zhao / chen_gong）
    layer: str        # fact / relation / state / social
    kind: str         # promise / help / event_result / stage_up / crisis / stance ...
    fact: str         # 确定性事实句，模板生成
    event_ref: str    # eventId，NPC 台词 → 事件的证据链
```

## 5. 四个投影（`app/engine/memory.py`，纯函数）

| 投影 | 输入 | 过滤与逻辑 | 对应机制文档 |
| --- | --- | --- | --- |
| `fact_memories(npc_id, tags, limit)` | 事件流 | 该 NPC 在场（或选项指向他）且带 `memory_tag` 的事件；按 `seq` 倒序 | 事实记忆 |
| `relation_memory(npc_id)` | 事件流 + 状态 | 关系阶段、该 NPC 的最近一次有效互动、首次知心时刻、重要共同事件 | 关系记忆 |
| `state_memory()` | 公开账本 | 近 3 月生命轨迹、最近一次晋升结果、连续加班月数（状态是"当前值"，不进事件流） | 状态记忆 |
| `social_stances(npc_id)` | 事件流 | 多人事件（`party_size > 1` 或多 NPC 在场）：玩家立场、对其他 NPC 的动作 | 社交记忆 |

规则：

- 事实记忆的 `fact` 文案 = 事件标题 + 选项摘要的固定模板，例如
  `「第 {month} 个月，{story_title}：你选择了「{choice_text}」。」`
- 陈工（`chen_gong`，无关系系统）只有事实记忆与状态记忆，不产生关系记忆、不触发邀约。
- 投影函数不得读取 `evidence_assessment` 的内容；隔离是双向的。

## 6. 读接口 `MemoryReadPort`

两个调用方（对话组装、触发器）只依赖这个接口，不直接摸事件流水：

```python
class MemoryReadPort(Protocol):
    def facts(self, npc_id: str, tags: Sequence[str] | None = None,
              limit: int = 5) -> list[MemoryItem]: ...
    def latest_interaction(self, npc_id: str) -> MemoryItem | None: ...
    def state_snapshot(self) -> StateSnapshot: ...
    def social_stance(self, npc_id: str, other_id: str) -> MemoryItem | None: ...
```

默认实现 `EventStreamMemory` 直接遍历事件流现算。将来若自由聊天升级为真 LLM
长对话、确需语义检索，仅替换该接口的实现（Mem0 / graph 类框架届时再评估），
调用方与契约都不变。

## 7. 主动消息触发器调度器（M3）

### 7.1 触发器定义（配置化，不硬编码在流程里）

每条触发器 = **条件谓词 + 文案模板 + 优先级 + 冷却月数**，集中在一张配置表：

| id | npc | 条件（谓词） | 优先级 | 冷却（月） | 对应机制文档 |
| --- | --- | --- | --- | --- | --- |
| `h_low_care` | 王哥 | 公开生命 ≤ 3 | 2 | 4 | 状态触发 |
| `overtime_care` | 小赵 | 连续加班 ≥ 3 月 | 2 | 4 | 状态触发 |
| `stage_up_invite` | 有关系系统的 NPC | 关系阶段刚刚 +1 | 1 | 2 | 关系触发 |
| `story_review` | 经历该事件的 NPC | 主线关键事件完成 | 1 | 3 | 剧情触发 |
| `promise_check` | 被承诺的 NPC | 存在未兑现的 `promise` 记忆 | 1 | 6 | 记忆触发 |

### 7.2 执行与记录

- 执行时机：**月末结算后** 与 **每次事件提交后** 各跑一遍；
- 每次命中写 `trigger_log(trigger_id, npc_id, month, message_id, seq)`；
  **冷却查询也查这张流水表**，与"记忆是投影"同一哲学，保证重放一致；
- 防轰炸：同一月按优先级取 top-K（K=2），同触发器冷却期内不重发；
- 消息体 = 模板 + 记忆槽位填充，`memoryRefs` 必填（对话与消息共用同一批证据引用）。

## 8. LLM 润色与降级（M4）

- 输入：`MemoryItem.fact`（模板句）+ NPC 人设 + 关系阶段 + 少量近期状态；
- 输出约束：**只许改写措辞**。后端校验关键槽位（事件名 / 月份 / 承诺内容）仍在句中，
  校验失败一律退回模板句；
- `generatedBy` 字段标记来源（`template` / `llm`），前端可见，便于排查；
- 无 LLM、无 Key、超时、限流：全部走模板，功能完整（规范要求的降级路径）。

## 9. 存储（M4 落库时）

| 表 | 内容 | 说明 |
| --- | --- | --- |
| `events` | 事件流水 | `sessionId + eventId` 幂等主键；`memory_tags` 随事件落库 |
| `session_state` | 状态快照 | 断线恢复用 |
| `trigger_log` | 触发器命中记录 | 冷却与审计查询走它，可复算 |
| `memory_game_view` | 游戏记忆投影（视图或缓存表） | 只读；如加缓存，键为 `(session_id, up_to_seq)` |
| `evidence_assessment` | 测评证据 | 与上一行**物理隔离**，不共用字段 |
| `report` | 报告 | 引用 `evidence_assessment` 的证据 id |

记忆本身不建可变表；投影缓存在规模允许前不加。

## 10. 对外接口

见 `contracts/openapi.yaml`（fixtures 在 `contracts/fixtures/npc-*.json`）：

| 接口 | 用途 |
| --- | --- |
| `GET /sessions/{id}/npcs/{npcId}/memories` | 四层记忆查询（记忆墙 / 对话上下文） |
| `POST /sessions/{id}/npcs/{npcId}/chat` | 自由聊天（幂等，返回回复 + memoryRefs + generatedBy） |
| `GET /sessions/{id}/messages` | 主动消息收件箱（冷却与优先级已在服务端算完） |
| `POST /sessions/{id}/messages/{messageId}/read` | 标记已读 |

`storyId` 在契约中是不透明字符串，契约 ID 与引擎事件键的映射留在后端内部。

## 11. 验收清单（对应机制文档 §12.3）

1. 同一 NPC 相邻两次对话引用的事实不重复（可程序断言）；
2. 任何一句 NPC 台词能通过 `memoryRefs[].eventRef` 回放到原始事件；
3. 触发器冷却生效：同一触发器在冷却期内不产生第二条消息；
4. 同一事件流重复计算投影，结果逐字节一致（确定性验收）；
5. 删除 LLM 配置后，对话与主动消息全部仍可生成（模板降级可用）；
6. `evidence_assessment` 中不存在任何来自 `chat` 事件的记录（防污染抽查）。

## 13. 待确认项

1. **承诺清单**：哪些选项算"做出承诺"？需要打分卡显式标 `promise` tag（阻塞 `promise_check` 触发器）；
2. **陈工的边界**：无关系系统，但他是否参与"状态触发"（如事故后的组内关心）？
3. **记忆墙的可见范围**：玩家在记忆墙能看到全部四层，还是仅 fact + relation？
   （影响 `/memories` 接口是否需要对 `state` / `social` 层做裁剪。）
