## 2. 三项待整改（对应 #4 / #5 / E 轴）

### 2.1 雷达满分口径（story_key_map #4）— ✅ 后端已重算，剩文档同步

- **现状**：`constants.RADAR_CAP_IN_DOC` 已在 2026-09-17 按 v3.0 在册 23 卡重写为 `{原则底线 23 / 执行交付 31 / 技术决策力 19 / 沟通协作 18 / 主动担当 17 / 抗压韧性 4}`；`radar.build_radar` 满分本就按在册卡**动态实算**，归一化不受影响。
- **未完成**：算法册 §9 的表值（40/33/33/31/23/14）仍是 39 件口径，未同步；且 `RADAR_CAP_IN_DOC` 注释标了「待办：表值→实算值」。
- **动作**：改文档表值即可，后端无需改代码。**唯一实质隐患是「抗压韧性」上限只有 4**（见 2.3）。

### 2.2 报告专题门槛（story_key_map #5）— ✅ 代码已覆盖，无需改

- **现状**：`TOPIC_MIN_EVIDENCE` 仍按 44 节点标定（如 NFC 3），但 `measure/topics.py` 的 `_module()` 用 **`displayable = n >= threshold`** 过滤——`n` 是运行时从在册卡样本实算的。样本不足的模块（NFC n=2<3）**自动 `displayable=False`，报告整体不渲染**，不会出错。
- **实测对照**：SDT 7✅、道德 13✅、CFC 8✅、rf两侧✅ → 只有 NFC 不出，而这是**预期行为**，非 bug。
- **结论**：NFC 现在就已经"降级不渲染"，无需改代码。若想**保留 NFC 维度**，才是补锚点（见长期项）。

### 2.3 大五 E + 抗压韧性 — ✅ 报告层已降级，长期靠补料

- **大五 E（外向）1 锚点** → `BIGFIVE_MIN_EVIDENCE=5`，`report/build()` 对大五每项输出 `behavior_available`，证据不足自动带「行为证据不足，仅供参考」（已实现）。E 轴不会硬出结论。**无需改代码**。
- **抗压韧性上限 4** → `radar.build_radar` 对 `RADAR_THIN_PILLAR="抗压韧性"` 已附弱标注 note「该柱机会少，样本由精力行为记录（硬扛/危险区/休息方式）补强」（已实现）。**无需改代码**。

## 3. 明确不需改（误导项澄清）

本核算澄清了三处**曾被误判、实测已达标/已收口**的点：
- **SDT=7**（非 4）：E14/E29/E39/E40/E41/E42/C5 均带 sdt，达标，**无需靠自由活动补**。
- **五处「选项方向相反」**：9-17 已全部按 `story_key_map` 逐条对齐（改 Godot 文案或改卡），`pendingRewrite=0`。
- **雷达满分代码**：`radar.build_radar` 已动态实算，不依赖 `RADAR_CAP_IN_DOC`。
