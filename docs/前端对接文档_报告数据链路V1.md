# 熊心壮职 · Agent 开发师 — 前端对接文档：报告数据链路 V1

对应《报告数据链路与算法设计 V2.3》§2 埋点与 §6 报告；接口字段以
`contracts/openapi.yaml` 为唯一准则，样例见 `contracts/fixtures/`（事件样例
`event-main-choice.json`，报告样例 `report-ready.json`）。

读者：游戏前端（Godot）、web 原型、鸿蒙壳的同学。讲两件事：
**① 你要在什么时机上报什么（第一部分）；② 你会拿到什么、怎么渲染（第二部分）。**

## 1. 总链路一张图

```text
玩家点击选项
  ↓ ① 前端上报原始行为（什么时候点的、犹豫多久、横跳几次）      ← 本文档第一部分
  ↓ ② 服务端按打分卡结算（六维/能力/大五/六专题证据累加）
  ↓ ③ M2 测量层（贝叶斯后验 / 专题聚合 / 雷达 / 投入结构）
  ↓ ④ M3 报告层生成三层报告（契约 Report 形状）
  ↓ ⑤ 前端拉取报告并渲染                                        ← 本文档第二部分
```

## 2. 三条红线（先读这个，违反即返工）

1. **前端只上报原始行为，不计算、不加工。** 客户端一旦能算出分（六维、大五、雷达……），
   抓包即拿到标定答案，整套测评被破解。前端要做的只有两件事：把玩家看到的渲染出来、
   把玩家做的原样记下来。
2. **打分卡（`data/story/scoring_cards.json`）的任何内容不得下发前端。** 服务端不会发，
   前端也不要问。选项文本走 `/sessions/{id}/next`。
3. **阈值与标定值永不出现。** 报告 JSON 里不会有任何门槛数字出现在文案中；
   `TopicModule.threshold` 仅供内测对账，客户端渲染时**忽略该字段**。

## 3. 第一部分：埋点上报

### 3.1 通用事件信封

所有埋点都走同一个接口：`POST /sessions/{sessionId}/events`（契约 `PlayerEvent`）。

```json
{
  "eventId": "9f1c…（uuid，前端生成，幂等键）",
  "eventType": "option_click",
  "contentVersion": "v1",
  "clientTime": "2026-09-14T20:30:00+08:00",
  "durationSeconds": 12,
  "payload": {
    "regionId": "B",
    "storyId": "E27",
    "choiceId": "E27-A",
    "hesitationMs": 14000,
    "switchCount": 3,
    "snapshot": { "life": 8, "money": 4200, "level": 3 }
  }
}
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `eventId` | **前端生成 uuid，同一次动作重试时必须复用同一个值**（服务端按它幂等：重发返回上次结果，不重复记） |
| `eventType` | 17 个测评埋点 + 2 个叙事事件，见 3.2 清单，**不要自创类型** |
| `payload.regionId` | 必填；不在区域内的动作（建档、报告页）填玩家当前所在区域 |
| `hesitationMs` | 从 `node_enter` 到确认的毫秒数，**原样上报，前端不取整不加工**；拿不到就省略，不要填 0 |
| `switchCount` | 选项间横跳次数（hover/焦点切换计数）；拿不到就省略 |
| `snapshot` | 选前公开账本快照（生命/金钱/职级等玩家可见值），用于服务端对账；拿不到就省略 |

失败处理：网络失败本地缓冲重试（指数退避，最多 5 次），重试**必须复用原 eventId**；
会话结束仍未上报成功的，下次启动补传。

### 3.2 十七个埋点清单（时机 + 必填 payload）

| # | eventType | 什么时候上报 | payload 必填/常用字段 | 干什么用 |
| --- | --- | --- | --- | --- |
| 1 | `profile_start` | 建档开始 | regionId | 自评先验起点 |
| 2 | `profile_answer` | 每答一题 | regionId, questionId, choiceId, durationSeconds | 自评先验 + 敷衍检测 |
| 3 | `manual_read` | 第 1 月读手册（每章节） | regionId, durationSeconds, skip | 动机信号（反复看「晋升通道」vs 跳过） |
| 4 | `event_trigger` | 主线事件触发 | regionId, storyId | 「这个事件为什么找上你」可解释 |
| 5 | `node_enter` | 进入决策点（选项出现） | regionId, storyId | 犹豫计时起点 |
| 6 | `option_hover` | 焦点在选项间切换（每次） | regionId, storyId, choiceId | 横跳计数（服务端也可由 switchCount 算） |
| 7 | `option_click` | 确认选项（**主埋点**） | regionId, storyId, choiceId, hesitationMs, switchCount, snapshot | 犹豫与摇摆主数据源 |
| 8 | `allocation_click` | 月度精力分配确认 | regionId, choiceId, snapshot | 价值排序 |
| 9 | `explore_click` | 自由周末选择 | regionId, activityId, npcId, snapshot | 投入结构 + 社交指纹 |
| 10 | `survival_state_change` | 生存轨状态变化（服务端通知驱动） | regionId | 处境轨迹 |
| 11 | `crisis_talk_choice` | 危机对话确认 | regionId, choiceId, hesitationMs | 归因指纹 |
| 12 | `monthly_action_variant` | 月度轻节点选择 | regionId, templateId, choiceId | 日常负荷 |
| 13 | `achievement_view` | 成就节点 C1/C2/C3 展示结束 | regionId, storyId, durationSeconds, skip | 参与度（C4/C5 是轻决策，走 option_click） |
| 14 | `zone_dwell` | 进出组团 | regionId, durationSeconds | 空间偏好（彩蛋） |
| 15 | `ai_reaction_view` | 反馈查看结束 | regionId, durationSeconds | 沉浸度 |
| 16 | `task_complete` | 第 48 月结束 | regionId | 触发报告生成的信号之一 |
| 17 | `report_view` | 报告每模块浏览（可聚合上报） | regionId, durationSeconds | 报告优化 |

另有 2 个叙事事件 `region_entered` / `npc_dialogue_complete`：只落日志不进测评，
照常上报即可。

**只记不算原则**：以上任何埋点都允许字段缺失（拿不到就别报错、别造假数据）；
服务端宁可少一条证据也不会因为缺字段崩。新增系统（熊友卡/训练谷/家园等）
**只记不用**——只落日志、不进测评，先不加新 eventType，找后端对口径。

### 3.3 报告生成的触发

玩家打完第 48 月（`task_complete` 上报后），前端调
`POST /sessions/{sessionId}/report`，返回 `{status}`；然后轮询
`GET /sessions/{sessionId}/report/status` 直到 `ready`，再
`GET /sessions/{sessionId}/report` 拉全文。`failed` 时给玩家一句通用
「报告生成失败，请重试」+ `reason` 原文，不要渲染堆栈。

## 4. 第二部分：报告渲染

### 4.1 Report JSON 长什么样

完整样例看 `contracts/fixtures/report-ready.json`。骨架：

```jsonc
{
  "sessionId": "…",
  "scoringVersion": "v2.9",
  "generatedAt": "…",
  "decisionCount": 103,
  "layers": {
    "persona": {            // 一层·职场人格画像（13 个模块都在这里）
      "personaSketch": "…",
      "bigfive": [ { "trait": "C", "traitCn": "尽责性", "self": 7.0,
                     "behavior": 4.1, "posterior": 5.2, "conflict": 1.8,
                     "conflictSignificant": true, "evidenceCount": 78,
                     "behaviorAvailable": true, "consistency": "situational",
                     "note": "你的这一面是有条件的…" } ],
      "selfVsBehaviorConflicts": [ { "traitCn": "…", "line": "…", "evidence": [ … ] } ],
      "radar": [ { "pillar": "原则底线", "score": 82, "cap": 40, "note": "" } ],
      "topics": [ { "key": "sdt", "title": "…", "displayable": true, "n": 20,
                    "summary": "…", "bullets": […], "evidence": [ … ] } ],
      "investment": { "weekendCounts": {"技术": 9}, "innerMotivation": 0.51, "line": "…" },
      "energyLedger": { "dangerZoneCount": 6, "pushedThroughCount": 4,
                        "recoveryWays": {"选择型休息": 3}, "line": "…" },
      "situationTrack": { "states": [ { "month": 15, "state": "observation" } ] },
      "promotionTrack": { "windows": [ { "seq": 1, "month": 6, "passed": true } ],
                          "finalGrade": { "grade": "中坚者", "line": "…" } },
      "sprintAndDisguise": { "sprint": […], "disguise": { "level": "low", "line": "…" } },
      "psychDriveHighlights": [ { "tag": "avoid_conflict", "line": "…", "evidence": {…} } ]
    },
    "market": { "dataSource": "stub", "jobs": [...] },   // 二层：JD 语料未接入前是 stub
    "crossHints": { "hints": [ { "line": "…", "basis": [ … ] } ] }
  },
  "evidenceReplay": [ { "seq": 12, "month": 6, "nodeId": "E07", "optionId": "C",
                        "hesitationMs": 14000, "switchCount": 3, "snippet": "…" } ]

```

### 4.2 五条渲染规则（算法册呈现铁律，前端必须执行）

1. **`displayable: false` 的 topic 模块整块不渲染**，连标题都不出——那是后端判定
   「证据不足不下结论」，不是数据缺失。
2. **`behaviorAvailable: false` 的大五特质只渲染自评条**，条旁固定标注
   `note`（「行为证据不足，仅供参考」），不要自己补一条空行为条。
3. **数值条用 `self / behavior / posterior` 画，文案只说档位。** 客户端不要把
   分数值以数字形式贴在「自评 vs 行为」文案旁（样例 UI 里的死数字只用于雷达分）。
4. **`psychDriveHighlights` 为空数组时整个模块不出**，不做补偿性推断。
5. **`market.dataSource === "stub"` 时二层渲染占位说明**（「岗位市场参考待接入」），
   不要拿 `jobs` 里的演示数据当真的。

`EvidenceRef`（evidence/evidenceReplay 里的小对象）统一渲染成「可展开的证据行」：
`snippet` 一句话 + 月份/犹豫/横跳标签；`hesitationMs` / `switchCount` 为 null 时
不显示对应标签。`month` 是该玩家自己的游戏内月份，直接显示没问题；
**不要**拿 `seq` 当月份显示（seq 是服务端统计序号）。

### 4.3 13 个模块 → 字段对照（速查）

| 报告模块 | 数据来源字段 | 渲染要点 |
| --- | --- | --- |
| 人格速写 | `persona.personaSketch` | 首屏大字；可能为空（专题全降级时），空则跳过 |
| 大五近似剖面 | `persona.bigfive[]` | 每特质三条：自评/行为/后验；规则 4.2-2 |
| 自评 vs 行为矛盾 | `persona.selfVsBehaviorConflicts[]` | `line` 直接展示 + 证据行 |
| 能力雷达 | `persona.radar[]` | score 0-100 六边形；`note` 非空时柱旁小字 |
| 专题模块（SDT/调节焦点/道德/归因/CFC/NFC） | `persona.topics[]` | `bullets` 渲染成 label: value 列表 |
| 投入结构 | `persona.investment` | `weekendCounts` 环形图 + `line` |
| 精力管理 | `persona.energyLedger` | 只用行为语言；**不给任何 H 数值**（后端也不发） |
| 处境轨迹 | `persona.situationTrack` | 时间线；`state` 中文映射由前端做（stable=稳定 等，见契约枚举语义） |
| 晋升轨迹与终局 | `persona.promotionTrack` | 7 窗时间线 + `finalGrade.grade` 徽章 |
| 冲刺与伪装 | `persona.sprintAndDisguise` | `disguise.level` 只决定配色深浅，`line` 才是文案 |
| 纯亏选择高光 | `persona.psychDriveHighlights[]` | 引用式排版（大引号块），有证据行 |
| 岗位市场参考 | `layers.market` | stub 占位，规则 4.2-5 |
| 交叉提示 | `layers.crossHints.hints[]` | 每条带 `basis` 证据行；页脚固定「提示，非结论」 |
| 行为证据回放 | `evidenceReplay[]` | 附录时间线，按 seq 升序 |

## 6. FAQ

- **Q：为什么犹豫时长/横跳要前端记？** 只有前端知道「选项出现到点击」的真实间隔，
  服务端只能算处理耗时。原样上报，别加工。
- **Q：`option_hover` 和 `switchCount` 重复了？** hover 是原始流水（可回放），
  switchCount 是汇总值。两个都发，服务端以 DecisionLog 落库为准，用 switchCount 对账。
- **Q：报告页要不要缓存？** 拉到 200 后可本地缓存（sessionId 维度）；
  重开游戏先查 `report/status`，`ready` 再用缓存。
- **Q：可以让报告接口快一点出吗？** 生成是异步的（算法链要跑完全部证据聚合），
  UI 做 loading 动画 + status 轮询（建议 1s 间隔，最多 30s，超时提示重试）。
